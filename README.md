# narray-linalg-bench

`Cumo::Linalg`（cuSOLVER実装）がnumo-linalg-altの`Numo::Linalg`と互換か、そしてCuPyと比べて速いかを、物理や解析で答えが決まる7つの題材で確かめる。narray-llmがLLMで果たした役割を、線形代数で果たすプロジェクト。

同じ題材を、同じアルゴリズムで、同じfixtureを読んで、4つの実装（Numo / Cumo / numpy+scipy / CuPy）で動かす。

## まとめ

GPUの数字はcumo 0.15.0（2026-11-03）で全138条件を測り直したものである。`Cumo::Linalg`が入った最初のリリースは0.12.0（2026-10-04）で、開発中のcumo masterで見つけた問題は、順に直って0.12.0に入った（経過は[docs/cumo-issues.md](docs/cumo-issues.md)）。CPUの数字は2026-10-01〜03に測った。

- **互換性**: 7題材すべてで、4実装が関門（物理や解析で決まる性質）を通り、物理量（エネルギー、尤度、RMSDなど）も一致した。NumoとCumoを直接比べた差（`test/test_parity.rb`）は、DFloatで相対1e-12、SFloatで相対1e-4に収まった。
- **`expm`の誤り**: 開発中のcumo master（`1c831278`）の`expm`は、1-ノルムの大きい行列で誤った答えを返した。Numoも同じように誤る。cumoがnumo-linalg-altのアルゴリズムをそのまま移していたためで、互換であることと正しいことは別だった。関門`expm_vs_eigh_wide_symmetric`で見つけたもので、cumoは#584で直った。0.12.0では、scipyとの差が相対1e-13以内に収まる。Numoの分は既知の失敗として`known_failures.json`に記録してある（[docs/cumo-issues.md](docs/cumo-issues.md)の2）。
- **速さの全体**: 138条件のうち、Cumoが速いのが66条件、遅いのが29条件、比が1をまたぐのが43条件だった。遅い29条件のうち20条件は、差が5%未満である。0.14.0のとき（速い65、遅い32、またぐ41）とほぼ同じである。0.15.0は`Cumo::Linalg`に手が入っておらず、0.14.0から動いた7条件で0.14.0と同じバッチに並べると、どれも比が1をまたいだ。
- **Cumoが速い経路**: 縦長の薄い`svd`（1.06〜1.65倍）、`lu_solve`（1.20〜1.93倍）、ガウス過程の`cholesky` + `cho_solve`（1.009〜2.015倍）、fp32の`lstsq`（1.09〜1.33倍）、ノルムの小さい行列の`expm`（1.09〜1.30倍）。
- **Cumoが遅い経路**: 小さいnの経済型`qr`（0.85〜0.99）、小さいnのRiccati（0.90〜0.99）、1-ノルムの大きい行列の`expm`（0.95〜0.98）、`eig`（0.95〜0.99）。nsysで数えると、小さいnの`qr`、`solve`、`cholesky`は、カーネル時間がCuPyとほぼ同じで、Cumoだけが1ステップに2〜5回同期していた（開発中の`1c561d70`で数えた。[docs/cumo-issues.md](docs/cumo-issues.md)の4）。cumo側ではこの同期には対応しないと決めた。`eig`の遅れはまだ調べていない。
- **開発中に直ったもの**: 経済型`qr`は`1c831278`では最大5.5倍遅かった。Rを取り出す`triu`が主因で、#585と#586で縮んだ（同じく1）。`cholesky`は利用者の`uplo`をそのままcuSOLVERに渡していたため、ガウス過程のn = 512のfp64で遅いアルゴリズムを通っていた。#587で、fillを型とnで選ぶようになった（同じく3）。
- **メモリ**: どの実装にもリークは無かった。Cumoのプロセスが1 GB前後になるのは、`require`の時点でCUDAのライブラリを一式読み込むためである。#583以降、最初のカーネルで増える量が85〜93 MB減った（[docs/memory.md](docs/memory.md)）。

## 数字

下の表は同じfixtureと同じアルゴリズムで、CumoとCuPyを並べたものである。4実装（Numo / Cumo / numpy / CuPy）すべてが関門を通ることを確かめてから測った（Numoの`expm`は既知の失敗）。

値は1ステップあたりのmsで、小さいほど速い。プロセスごとのbest-of-3を10ラウンドぶん取り、その中央値をとった。11ラウンド回し、最初の1ラウンドは値を見ずに捨てた。1ラウンドの中ではCumo、CuPy、対照（Cumoをもう一度）の3系列を直列に走らせ、系列の順序をラウンドごとに回した。1プロセスが2秒以上回るように、条件ごとに回数を選んである（`bench/conditions.tsv`）。

比は「CuPy ÷ Cumo」で、同じラウンドどうしの比の中央値である。1を超えればCumoが速い。後ろのn/10は、10ラウンドのうち比が1を超えた（Cumoが速かった）回数である。10ラウンドの比の最小値と最大値が1を挟んだ条件には、「またぐ」と付けた。比の大きさが決まらなかったという意味である。対照（Cumoどうしの比）は全条件で1をまたいだ。

cumoはrubygemsの0.15.0、CuPyは14.2.0である。クロックは`nvidia-smi -lgc 3090` / `-lmc 14001`で固定した。2026-11-03 01:37から05:50にかけて、GPUの全138条件を同じビルドで測った。表には代表の条件だけを抜き出した。全条件は各表の下にリンクした結果ファイルにある。

- **CPUの値は幅が大きい。** プロセス単位で1.6〜3.8倍遅い回が散発する。原因は調べていない。「またぐ」の付いた行は比の大きさを読まないこと。
- `lu_solve`はnumpyが6〜42倍速い。どちらも`getrs`を1回呼ぶだけなので、numo-linalg-altの呼び出しの前後の処理が重いと疑っている（[docs/numo-linalg-alt-notes.md](docs/numo-linalg-alt-notes.md)の4）。
- `expm`は、numo-linalg-altがPadé(8)、scipyがAl-Mohy & Higham（2009）で、アルゴリズムが違う。
- Aの`eigh(H, S)`のfp32はn = 4096の代わりにn = 2048を載せた。numo-linalg-altのSFloatの一般化`eigh`はn ≥ 2895で誤った答えを返すためである（同じく7）。
- GPU対CPUの比（Numo ÷ Cumo、numpy ÷ CuPy）は各題材の結果ファイルにある。fp32の最大のサイズでは、どの経路でもGPUが速い（Numo ÷ Cumoで2.1〜81倍、numpy ÷ CuPyで1.3〜88倍）。小さいn（64〜256）では、fp32でもCPUが速い条件がある（CのRiccatiのn = 64でNumo ÷ Cumoが0.5）。fp64はGPUが1/64レートなので、差が小さい。

## CuPyには無くCumo::Linalgにはある関数

CuPy 14.2.0の`cupy.linalg`と`cupyx.scipy.linalg`に無いもの。Python側の代わりの組み方は[docs/cupy-gaps.md](docs/cupy-gaps.md)にある。

- `ldl`（Bunch-Kaufman分解）。単発の値で、n = 4096のfp32のKKT行列に69 ms（Numoとnumpyは約437 ms）。
- 一般化固有値問題`eigh(a, b)`と`eigvalsh(a, b)`。CuPyでは`cholesky`と`solve_triangular` 3回と`eigh`で組むことになる。
- `cho_fact` / `cho_solve` / `cho_inv`、`lu_inv`、`null_space` / `orth`、`svdvals`。

## 見つかった問題

- cumo: [docs/cumo-issues.md](docs/cumo-issues.md)（`expm`が誤る、経済型`qr`の上乗せ、`cholesky`の速さが`uplo`で変わる。どれも0.12.0の前に直った。0.13.0で小さいnの`expm`が遅くなった件は、0.14.0で直った。小さいnで呼び出しごとの同期が残ることは、cumo側で対応しないと決めた）
- numo-linalg-alt: [docs/numo-linalg-alt-notes.md](docs/numo-linalg-alt-notes.md)（`expm`が誤る、SFloatの一般化`eigh(a, b)`がn ≥ 2895で例外を出さずに誤る、SFloatの`lstsq`のデバッグ出力、横長の行列で`orth`が落ちる、`matrix_power`が二乗法でない、`lu_solve`が遅い）

## 使い方

```
bundle install
python3 -m venv python/.venv
python/.venv/bin/pip install -r python/requirements.txt

rake fixtures                           # data/ に small fixture を作る
rake test                               # GPU 無しで全部通る（cumo が入っていれば parity も回る）
ruby script/gate.rb                     # 関門（Numo、fp64）
GPU=1 ruby script/gate.rb               # 関門（Cumo）
python/.venv/bin/python python/gate.py  # 関門（numpy。GPU=1 で CuPy）
ruby script/compare_gates.rb tmp/gates/*.json   # 4 実装の関門と物理量を並べる
rake bench                              # GPU の表（クロックの固定が要る）
rake bench:cpu                          # CPU の表
```

Cumoはrubygemsの0.15.0を`vendor/cumo-0.15.0/`にビルドしたものを使う。Gemfileには入れていない。手順は[AGENTS.md](AGENTS.md)の「cumoの版」にある。計画は[docs/plans/PLAN-linalg-bench.md](docs/plans/PLAN-linalg-bench.md)、比較の条件は[docs/method.md](docs/method.md)にある。
