# cumoで見つけた問題

性能で負けた条件、互換性が崩れた箇所、その原因の仮説を記録する。棄却した仮説も消さずに残す。cumoの版は文字列ではなくコミットで書く（AGENTS.mdの「cumoの版」）。

## 直す候補（cumo 0.15.0、2026-11-03）

まだCuPyより遅い条件を、遅い順に並べた。値はCuPy ÷ Cumo（CuPyと並べた10ラウンド）で、1より小さいほどCumoが遅い。0.15.0は`Cumo::Linalg`に手が入っておらず、順位は0.14.0のときと変わらない。

| 順 | 条件 | 0.15.0 | 0.14.0 | 見立て |
|---|---|---|---|---|
| 1 | e_qr m4096 n16 fp32 | 0.852 | 0.852 | `getrf`のdevInfoの同期1回（4、cumoセッションが確認済み） |
| 2 | c_riccati n256 fp32 / n64 fp64 | 0.900 / 0.904 | 0.869 / 0.913 | 小さいnの同期（4）。n256 fp32は0.14.0のときに下がったが、0.12.0のとき（0.905）の水準に戻った。測った日による違い |
| 3 | e_qr m16384 n16 fp32ほかn = 16の`qr` | 0.921〜0.984 | 0.915〜0.974 | 1と同じ |
| 4 | a_eigh_general n128 fp32 | 0.940 | 0.933 | 小さいn。同期回数は未計測だが、cumo側では同じ小さいnの同期（4）として扱う |
| 5 | c_expm n64 fp32 / fp64 | 0.947 / 0.947 | 0.935 / 0.952 | 0.13.0の後退は#618で戻った（5、解決）。残るのは0.12.0のときからある差 |
| 6 | c_expm n1024 / n4096 fp32 | 0.952 / 0.958 | 0.949 / 0.954 | n1024は#595で0.867から縮まった |
| 7 | f_eig n256 fp32 / fp64 | 0.954 / 0.962 | 0.952 / 0.966 | 0.12.0のときより約1.5%悪い。0.13.0と0.12.0のA/Bでも同じ向き（0.986、0.989）。コードの配置だけで出る幅（1.5〜2.6%）に入るので、どの変更のせいかは決めていない（未調査） |

1〜4は小さいnの呼び出しごとの同期（4）で、cumo側では対応しないと決めた。残るのは5〜7である。7の0.12.0からの悪化は、配置の揺れの幅に入る。

## 未解決

### 4. 小さいnの`solve`と`cholesky`で、呼び出しごとの同期が残る（2026-10-03、master `1c561d70`）

**cumo側では、この同期には対応しないと決めた。** 下の記録は、その判断の材料として残す。

#586でgeqrf、orgqr、getrs、potrsはdevInfoを読まなくなった。それでも、小さいnの条件ではCumoだけが同期する。nsysで数えた1ステップあたりの値（`--inner` 100と200の差を100で割った。回数は確定、時間は1組のprofileなので目安）。

| 条件 | Cumo | CuPy |
|---|---|---|
| E `qr` m = 4096, n = 16 fp32 | カーネル30本 / 117 µs、`cudaStreamSynchronize` 2回 | 29本 / 96 µs、同期0回 |
| A `cholesky` + `solve` n = 128 fp32 | 29本 / 384 µs、`cudaStreamSynchronize` 5回、`cudaMallocManaged` 2.9回 | 38本 / 370 µs、同期0回 |
| C Riccati n = 256 fp32 | 30本 / 129 µs、`cudaStreamSynchronize` 2回 | 30本 / 131 µs、同期0回 |

- この3条件では、カーネル時間はほぼ同じで、CuPy ÷ Cumoは0.81〜0.92である。差は同期から来ている疑いがある。同期だけを足した対照では確かめていない。
- 残っている同期は、`getrf`と`potrf`のdevInfoの読み戻しだと思われる。特異行列や正定値でない行列を検出するのに使っているので、#586と同じようには外せない。
- 0.12.0（#588で、小さい行列の`cholesky`と`solve`の待ちを一部省いた）では、上の3条件のCuPy ÷ Cumoが0.844、0.972、0.905になった。同期の回数は数え直していない。
- 0.14.0（2026-10-18）では、上の3条件のCuPy ÷ Cumoが0.852、0.974、0.869だった。Riccatiが0.12.0のときより下がったのは、0.13.0と同じバッチでは差が無いので、版ではなく測った日による違いである。
- 0.15.0（2026-11-03）では、上の3条件のCuPy ÷ Cumoが0.852、0.980、0.900だった。Riccatiは0.12.0のときの水準に戻った。
- 2026-10-05にcumoのセッションが、Eの`qr`のm = 4096, n = 16で、同期だけを足した対照を測った。CuPyの1ステップの末尾に同期を1回足すと、fp32で0.117 msから0.134 msになり、Cumoの0.137 msとほぼ並んだ（fp64は0.416 ms対0.416 ms）。この条件の差は、ほぼ全部が`solve`の中の`getrf`のdevInfoを読む同期1回だった。こちらでは測り直していない。

## 解決済み

1〜3は、2026-10-03に直した版のmaster（1と2は`aaa3162b`と`1c561d70`、3は`50e07e88`）で確かめた。5は、2026-10-18にリリースの0.14.0で確かめた。どれも、直す前のビルドと同じバッチに並べた。

### 1. `qr(mode: 'economic')`に1回あたり約0.3〜0.5 msの上乗せがあり、主因は`triu`（2026-10-02、master `1c831278`）

Eの`qr`経路（`qr(V, mode: 'economic')` + `solve(R, Qᵀy)`）で、Cumoは18条件すべてCuPyより遅い。m = 4096, n = 16のfp32では0.650 ms対0.118 msだった（[results/vandermonde_lstsq.md](results/vandermonde_lstsq.md)）。

nsysで数えた。`--inner` 100と200の2本を取り、その差を100で割っている。1ステップあたりの値。

| | Cumo | CuPy |
|---|---|---|
| カーネル | 38本 | 29本 |
| `cudaDeviceSynchronize` | 2回 | 0回 |
| `cudaStreamSynchronize` | 11回 | 0回 |
| `cumo_iter_int64_store_int32_kernel_dim1` | 1本、265 µs | — |

演算を単独で呼んで切り分けた（1回あたり。同じく差分法）。

| 単独で呼んだもの | カーネル | GPU時間 | 同期 |
|---|---|---|---|
| `qr(v, mode: 'economic')` | 24本 | 509 µs（うち`int64_store_int32`が347 µs） | `cudaDeviceSynchronize` 2回、`cudaStreamSynchronize` 6回 |
| `solve(r, qᵀy)` | 13本 | 26 µs | `cudaStreamSynchronize` 5回 |
| `v[0...16, true].triu` | 10本 | 106 µs（うち`int64_store_int32`が91 µs） | `cudaDeviceSynchronize` 2回、`cudaMallocManaged` 9回 |

- **`qr`の上乗せの大半は、Rを取り出す`triu`から来ている。** `triu`単独でも、同じカーネル、2回の`cudaDeviceSynchronize`、Bitのcountの縮約が出る。`Cumo::Linalg.qr`は`qr[0...n, true].triu`（economic）または`qr.triu!`を呼ぶ。
- 16要素ほどのstoreに91〜347 µsかかっている理由は調べていない。時間は1組のprofileから出したもので、目安である。回数は確定している。
- CuPyの1ステップは、`cudaStreamSynchronize`が0回だった。devInfoを同期して読まないことは、これで確かめた。Cumoは`solve`だけでも5回同期する。

**#585（`triu` / `tril`のカーネル化）で直った。** m = 4096, n = 16のfp32で、1ステップが0.662 msから0.175 msになった（旧÷新3.81、10/10）。ただしCuPy ÷ Cumoはまだ0.698（0/10）で、CuPyの0.116 msより約0.05 ms遅い。n = 256では0.96〜0.99、m = 65536, n = 256では0.945だった（[results/vandermonde_lstsq.md](results/vandermonde_lstsq.md)）。残りの差の内訳は、nsysで数え直していない。

#586（geqrfとorgqrのdevInfoを読まない、作業領域を持ち続ける）のあと、`1c561d70`では0.808になった。同じバッチで、`aaa3162b`より1.20倍速い。残りの差は、上の4で扱う。

### 2. `expm`が、1-ノルムの大きい行列で誤った答えを返す（2026-10-02、master `1c831278`）

**性能ではなく正しさの問題である。** cumoの`Cumo::Linalg.expm`はnumo-linalg-altと同じアルゴリズム（Padé(8)に固定、scalingの回数はmax|aᵢⱼ| から決める）なので、numo-linalg-altと同じく、要素は小さくても1-ノルムが大きい行列で精度を失う（[numo-linalg-alt-notes.md](numo-linalg-alt-notes.md)の0）。

| 行列（fp64） | scipyの`expm`との相対差（Cumo） | 同（CuPy） |
|---|---|---|
| CのA_c、n = 256（1-ノルム167） | 3.2e-7 | 1.3e-14 |
| CのA_c、n = 1024（1-ノルム623） | 9.4e-3 | 4.9e-14 |
| CのA_c、n = 4096 | 1.15 | 1.9e-13 |
| 要素[−1, 1]の対称行列、n = 256：V diag(e^λ) Vᵀ との相対差 | 2.95e-5 | 1.1e-14 |

- 関門`expm_vs_eigh_wide_symmetric`（Cのsmall fixture）で検出している。NumoとCumoは`known_failures.json`に既知の失敗として記録してある。直ったら、関門が通って`rake test`が落ちるので、記録を消すこと。
- **numo-linalg-altと結果が一致する（互換である）ことと、正しいことは別である。** NumoとCumoのparityテストは、この入力でも通る（どちらも同じように誤る）。
- Cの計測では、`expm`でCumoがCuPyより1.13〜1.66倍速く出たが、Cumoはscalingが少ないぶん積の回数も少なく、答えも誤っている。**速さの比較としては無効**として扱う（[results/kalman_riccati.md](results/kalman_riccati.md)）。
- Fの`expm`（Q = P − I、1-ノルム2程度）は、Cumoもscipyと1.2e-15で一致する。こちらの計測では答えは正しいが、Padé(8)とPadé(13)でアルゴリズムが違う。

**#584で直った。** `ord`を省略すると、scipyと同じAl-Mohy & Higham（2009）の方式で次数とscalingの回数を選ぶ。`ord`を渡すと、従来の固定次数のまま動く。

| CのA_c（fp64） | 1-ノルム | 旧`1c831278` | 新`aaa3162b` |
|---|---|---|---|
| n = 256 | 167 | 3.2e-7 | 6.7e-15 |
| n = 1024 | 623 | 9.4e-3 | 2.7e-14 |
| n = 4096 | 2412 | 1.15 | 1.0e-13 |

- 関門`expm_vs_eigh_wide_symmetric`は、Cumoで4.2e-15になった。`known_failures.json`の記録は、Numoだけに直した。
- 速さは、Cの行列（1-ノルムが大きい）で旧の1.32倍遅くなり、CuPy ÷ Cumoは0.86〜0.91になった。Fの行列（1-ノルムが小さい）では逆に旧より1.25倍速くなり、n = 4096のfp32でCuPy ÷ Cumoは1.147になった（[results/kalman_riccati.md](results/kalman_riccati.md)、[results/markov_diffusion.md](results/markov_diffusion.md)）。

### 3. `cholesky`の速さが`uplo`で大きく変わり、CuPyと別のアルゴリズムを通る（2026-10-03、master `1c561d70`）

Cumoは行列を列優先に写し直し、`uplo`をそのまま`cusolverDnXpotrf`に渡す。CuPyの`cholesky`は、常に`CUBLAS_FILL_MODE_UPPER`を渡す。nsysで見ると、Cumoの`uplo: 'L'`はcuSOLVERの中で`getrf_wo_pivot`カーネルを1本走らせ、CuPyは`potrf_alg2_*`を何本も走らせる（Bのn = 512のfp64で48本）。

単発の値（best-of-3 × 50回。`bench/run.sh`ではない）。単位はms。

| 型 | n | Cumo `'L'` | Cumo `'U'` | CuPy |
|---|---|---|---|---|
| DFloat | 512 | 1.291 | 0.829 | 0.811 |
| DFloat | 1024 | 2.692 | 2.792 | 2.752 |
| DFloat | 2048 | 8.514 | 13.238 | 13.113 |
| SFloat | 512 | 0.144 | 0.235 | 0.220 |

- `'U'`はCuPyとほぼ同じ時間になる。`'L'`は`'U'`と比べて、DFloatのn = 512で1.56倍遅く、n = 2048で1.55倍速い。
- BのGP（`uplo: 'L'`）で、Cumoがn = 512のfp64で負け（0.678）、n ≥ 2048で勝つ（1.3〜1.6倍）のは、これから来ている疑いがある。`bench/run.sh`を`'U'`で回しては確かめていない。
- 入力が対称なら、列優先への写し直しを省き、fillを反転させて渡せば同じ答えになる。写し直しのカーネル（Aのn = 128で1ステップ7本、32 µs）も消える。提案であり、試していない。

**#587で直った。** cuSOLVERに渡すfillを、`uplo`ではなく型とnで選ぶようになった（DFloatのn < 800と、すべての型のn < 32はU、それ以外はL）。`50e07e88`で、BのGPのn = 512のfp64はCuPy ÷ Cumoが0.678から0.986になった。同じバッチで、`1c561d70`より1.46倍速い。Lを通って勝っていたn = 2048は、fp32で1.525、fp64で1.383のまま残った（[results/gaussian_process.md](results/gaussian_process.md)）。

### 5. 0.13.0で、小さいnの`expm`が0.12.0より遅くなった（2026-10-12、cumo 0.13.0）

Cの`expm`（`expm(A_c)`）のn = 64で、0.13.0が0.12.0より遅い。同じバッチに並べた6ラウンドで、すべて0.13.0が遅かった（[results/kalman_riccati.md](results/kalman_riccati.md)）。

| 条件 | 0.13.0 | 0.12.0 | 0.12.0 ÷ 0.13.0 | 対照 |
|---|---|---|---|---|
| C `expm` n = 64 fp32 | 0.500 ms | 0.474 ms | 0.940 0/6 | 1.015 4/6、1をまたぐ |
| C `expm` n = 64 fp64 | 0.592 ms | 0.574 ms | 0.970 0/6 | 1.000 3/6、1をまたぐ |

- n = 256は0.997〜1.001で、遅れはn = 64でだけ見えた。n = 1024のfp32は逆に1.092倍速い（#595）。
- A_cは64×64の密な非対称行列で、1-ノルムは42.0。最初の`adaptive_pade_expm`でd4、d6、d8が有限になり、s > 0で`square_exp`に進む（prescaleの経路には入らない。cumoのセッションの指摘で訂正した）。
- 同期の回数は、`CUMO_SHOW_WARNING=ON CUMO_SHOW_WARNING_ONCE=OFF`で数えると、新旧とも`expm` 1回あたり4回で同じだった。0.12.0はsfloatの`to_a`が3回と`extract_cpu`が1回。0.13.0はsfloatの`to_a`が2回、uint64の`to_a`が1回、`extract_cpu`が1回。
- #600でノルムの読み戻しが1回減り、その代わりに#609の`triangle_parts`（三角行列かどうかの判定）で`count_true(...).to_a`が1回増えたように見える。`triangle_parts`は2乗が要る経路で毎回呼ばれ、10本前後のカーネルを足す。A_cは三角ではないので、判定の結果は使われない。
- 2026-10-12にcumoのセッションが確かめた。`triangle_parts`を外すだけで、fp32は9.4%、fp64は5.4%速くなった（6ラウンド交互、6/6）。`triangle_parts`は単体で約31 µsかかり、同期は約7 µs、残りは10本前後のカーネルの起動だった。
- PR #618（master `ba55f179`、0.14.0に入った）で直った。上三角なら左下、下三角なら右上の角が必ず0になるので、両方の角が0でなければ判定を省く。角の値は、最初の`onenorms`の読み出しに相乗りさせる。cumoの計測（64×64、6ラウンド交互、対照付き）では、kalman型がfp32で8.1%、fp64で5.6%、SComplexで7.1%速くなり、fp32は0.466 msだった。2乗の要らない小さいノルムの行列は、角の読み出しの分（2〜3 µs）だけ約1%遅くなる。
- 角が0の非三角行列（ヘッセンベルグ、帯、ブロック対角）では、遅れが残る。
- **0.14.0で直った。** 2026-10-18に、0.14.0と0.13.0を同じバッチに並べた（6ラウンド）。0.14.0がfp32で1.077倍（0.471 ms対0.506 ms）、fp64で1.046倍（0.571 ms対0.597 ms）速く、6ラウンドすべてで0.14.0が速かった。CuPyとの比は、fp32で0.935、fp64で0.952で、0.12.0のとき（0.931、0.932）の水準に戻った（[results/kalman_riccati.md](results/kalman_riccati.md)）。
